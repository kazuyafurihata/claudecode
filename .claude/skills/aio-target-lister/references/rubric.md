# 相性判定のルーブリック

AIOマスターの仕様から逆算した判定基準。判定に迷ったとき、または
「なぜこの会社がSなのか」を台帳の読者に説明するときに使う。

## 前提：AIOマスターとは何か

`references/aio_product.md` を先に読む。要点は：

- ChatGPT等のAI検索で、**非指名の50問**を定点観測する
- 掲載されたら**1問1万円**の成果報酬

この2点から、相性は次の2つに還元される。

1. **掲載される余地があるか**（そもそもAIに聞かれる質問が立つ業種か）
2. **掲載が売上につながるか**（1回挙がることの金額的な意味）

判定文をこの2点に紐づけて書くと、営業が商談でそのまま喋れる。

## 4つの判定軸

| 軸 | 見るもの | 強い例 / 弱い例 |
|---|---|---|
| 非指名検索の有無 | 顧客が社名ではなく「地域＋業種」「課題＋解決策」でAIに聞くか | 強：士業・クリニック・人材・不動産・Web制作 ／ 弱：指名買いのメーカー・受託製造 |
| 比較検討市場の厚み | 競合が多く比較されるか。成果報酬なので質問が立たないと課金も起きない | 強：都市部の同業多数 ／ 弱：ニッチすぎて質問自体が立たない |
| 再販できる立場か | 顧客基盤を持っているか。1社が数十社の販売に化ける | 強：Web制作・広告・コンサル・人材 ／ 弱：一般事業会社 |
| 既存の接点の濃さ | 契約・請求・協業が動いているか。提案の摩擦が最小 | 強：件名に契約/請求/協業 ／ 弱：一斉配信に入っているだけ |

## Tierの定義

軸の合計点ではなく、**次に打つ手が同じ会社をまとめる**のがTier。
台帳を見た営業が「この塊は今日こう動く」と分かる単位にする。

| Tier | 名前（例） | 中身 | 打ち手 |
|---|---|---|---|
| S | いま出せば決まる | AIOの商談が動いている、または契約・請求が走っていて提案の話を持ち込みやすい | 追いかけ。最終接触からの日数を必ず書く |
| A | 非指名検索が売上に直結する | 顧客が「地域＋業種」でAIに聞く業種。成果報酬の説明が通る | 新規提案。業種ごとの質問例を添える |
| B | 掲載価値はあるが自社導入型 | 来店・来院・地場の集客型。効くが1社1件 | 単体導入の提案 |
| C | AIOより先に別の話題がある | 指名取引・受託製造・BtoB専業など | 自社の既存サービスや近況の確認から入る |

Tier Cは「AIOに向かない」と断じる欄ではない。ほとんどの場合
**件名からAIO文脈が読み取れなかった**だけなので、台帳の注記でもそう書く。
断定すると、実際は有望な先を営業が自分で消してしまう。

## 再販できる先（`partner`）の扱い

顧客基盤を持つ会社に「自社の顧客にも紹介しませんか」と持ちかけると、
1社の接点が数十社の販売に化ける。ただし**紹介・再販の条件は利用者が
勝手に決められない**ことがある。台帳の注記では「紹介スキームはライトアップ担当に
相談のうえ提案」と添え、条件を約束する書き方はしない。

## 相性の良い業種

士業（司法書士・税理士・社労士）／ クリニック・歯科 ／ 美容・サロン ／
不動産 ／ 工務店・リフォーム ／ 介護・障がい福祉 ／ 教室・スクール ／
制作会社・代理店

共通点は「地域名＋業種」で比較検討されること、そして1件あたりの単価が高いこと。
逆に単価の低い日用品や、指名買いが中心の商売とは相性がよくない。

## カテゴリ（フィルタのチップ）

`cat` に入れる値。台帳のフィルタはこれで動く。

| key | ラベル | 入るもの |
|---|---|---|
| `partner` | 再販・紹介 | 顧客基盤を持ち、紹介・再販から入るべき先 |
| `web` | Web・広告 | 制作・広告・SEO |
| `consul` | コンサル・士業 | 士業、経営コンサル、支援機関 |
| `hr` | 人材・HR | 人材紹介、採用支援 |
| `it` | IT・SaaS | 開発会社、SaaS事業者 |
| `estate` | 不動産・建築 | 不動産、工務店、リフォーム |
| `med` | 医療・介護 | クリニック、歯科、介護、障がい福祉 |
| `shop` | 店舗・飲食 | 来店型、飲食、サロン、教室 |
| `other` | その他・要確認 | 判定できなかった先 |

`partner` は業種ではなく立場なので、Web制作会社でも再販が狙えるなら
`web` ではなく `partner` に置く。フィルタで「再販できる先だけ」を
一覧したい場面が実際にいちばん多い。

## 確からしさの表示（`tag`）

| tag | 表示 | 意味 |
|---|---|---|
| `aio` | AIO | AIOの商談がすでに動いている（件名に根拠がある） |
| `fact` | 確 | 件名から業務内容が確認できた |
| `ask` | 推 | ドメイン名からの推定。提案前に事業内容の確認が要る |

ドメイン名だけで業種を決めた会社に `fact` を付けない。
台帳の価値は網羅性ではなく、**どこまでが事実でどこからが推定か**が
一目で分かることにある。ここを曖昧にすると、営業が推定を事実として
商談で喋り、一度で関係が壊れる。

## 社名の付け方

メールの署名や件名に社名が出ていればそれを使う。出ていなければ
ドメインから読める範囲で書き、`tag: "ask"` にする。**Web検索で社名や業種を
調べて埋めない**（件数が多く時間がかかるうえ、同名他社を拾う事故が起きる）。
裏取りは台帳を見た営業が、連絡する直前に1社ずつやる。
