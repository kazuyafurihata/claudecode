# 法務リーガルチェック スキル（ライトアップ向け）

## このスキルの目的

ライトアップ社の事業部担当者が、顧客から届いた契約書や修正コメント入り契約書について、法務（村越氏）に正式依頼する前に **"どの条項が指摘されそうか" と "理想的な改定文案"** を先取りで把握できるようにするスキル。雛形種別を判定し、適切な範囲でチェックを行い、法務への依頼メール下書きも自動生成する。

**基本方針**：
- **先方配慮重視**：顧客との関係性を重視し、過度な要求は避ける
- **リスク重点絞り込み**：法的効力に直接影響する高リスク事項、村越氏の定番指摘事項のみに絞って確認
- **業界慣行内は許容**：一般的な商慣行の範囲内の調整は基本的に受入方向
- **落としどころ志向**：「死守すべき」ではなく「ご判断」を仰ぐ相談スタンス
- **雛形種別対応**：ライトアップ雛形は変更箇所のみ、先方雛形は全文チェック

## トリガー条件

以下のいずれかに該当する場合、このスキルを使う：

- 契約書ファイル（.doc / .docx / .pdf）をアップロードし「チェック」「レビュー」「赤字」「変更履歴」などを依頼
- メッセージに「契約書」「リーガル」「NDA」「業務委託」「業務提携」「代理店」「覚書」「紹介契約」「利用規約」「金銭消費貸借」などの語が含まれる
- 「先方から戻ってきた契約書を見てほしい」「村越さんに指摘されそうな箇所」等

## ワークフロー（必ずこの順序で実行）

### ステップ0a. 雛形の種別判定（重要）

契約書をアップロードした際、必ず対話でユーザーに確認する（AskUserQuestion 相当。ツールが無ければ通常の質問文で確認）。次の2択から選んでもらう：

- **ライトアップ雛形**（当社→先方送付後、赤字修正で戻ってきたもの）
- **先方雛形**（先方作成・提供の雛形を当社が初回確認）

回答による**チェック範囲の違い**（以降のステップ1・4で参照する基準）：
- **ライトアップ雛形** → 赤字・変更履歴箇所**のみ**をチェック
- **先方雛形** → **全文**をチェック（抽出結果が0件でも全条項をパターンライブラリと照合）

ユーザーの回答を受け取ってから、以降のステップに進む。

### ステップ0b. ファイル形式の確認と変換

アップロードされたファイル拡張子を確認：

- `.docx` → そのまま使用
- `.doc`  → **旧形式は本スキルでは直接処理できない**。ユーザーに「Word で開き `.docx` 形式で保存し直してから再投入」を依頼する（自動変換は行わない）。
  - 注記：この環境には libreoffice/soffice は未インストール。Word の COM 変換は確実性未検証のため、当面は上記の手動 .docx 保存を基本手順とする。
- `.pdf`  → pdf スキルでテキスト抽出。ただし赤字・変更履歴は失われるため、可能なら .docx 原本を要求

### ステップ1. 変更箇所の自動抽出

`scripts/extract_review_targets.py` を実行し、先方が加筆した箇所を抽出する：

中間ファイル `targets.json` はセッションのスクラッチパッドに出力する（作業ディレクトリ直下には置かない）：

```bash
python scripts/extract_review_targets.py -i <契約書.docx> -o <スクラッチパッド>/targets.json --verbose
```

このスクリプトは以下を検出する：

- **赤文字**: 色コード FF0000 系で明示された文字
- **ハイライト**: 蛍光ペン・背景色
- **トラックチェンジ挿入（w:ins）**: 変更履歴による追加（作成者・日時付き）
- **トラックチェンジ削除（w:del）**: 変更履歴による削除
- **コメント（w:comment）**: 先方が入れたコメント

**雛形種別による処理の分岐**：

**🔸 ライトアップ雛形の場合**：
- 抽出結果が 0 件 → ユーザーに「変更履歴が無い清書版のようです。赤字版はありますか？」と確認
- 抽出結果が 1 件以上 → ステップ4で**抽出箇所のみ**を重点的に精査

**🔸 先方雛形の場合**：
- 抽出結果の件数に関わらず、ステップ4で**全条項**をパターンライブラリと照合
- 抽出結果がある場合は「先方が特に変更・強調している箇所」として参考程度に活用

### ステップ2. 契約書種別の判定

契約書タイトル・前文・第1条を読み、以下の9カテゴリに分類：

1. nda — 秘密保持契約
2. gyomu-itaku — 業務委託契約書
3. gyomu-teikei — 業務提携契約書（紹介業務委託、販売業務委託を含む）
4. dairiten — 代理店契約書・販売店契約書
5. jinzai-shokai — 人材紹介契約
6. kakoyo — 覚書（契約変更・終了・CSR・返金等）
7. ryakin-shohi — 金銭消費貸借契約書
8. riyo-kiyaku — 利用規約・申込規約
9. kojin-joho — 個人情報取扱契約・覚書

判定に迷う場合はユーザーに確認。

### ステップ3. パターンライブラリの参照

判定した種別に応じて `references/patterns-common.md`（共通）と `references/patterns-{カテゴリ名}.md` を Read する。共通パターンは必ず読む。

### ステップ4. 契約書精査と指摘生成

**🔸 ライトアップ雛形の場合**：
ステップ1の抽出結果を起点に、パターンライブラリと照合して指摘を生成する。

**🔸 先方雛形の場合**：
全条項をパターンライブラリと照合し、高リスク事項・定番指摘事項を抽出する。
具体的には、契約書の以下の条項を重点的に確認：

- **知的財産権の帰属**（著作権・特許権等の帰属先、帰属時期）
- **損害賠償・責任制限**（⚠️定番：片務→双務化が必須。対顧客契約では「乙のみ賠償義務」は必ず双務に修正。上限設定の有無・相互性・除外事由も確認）
- **秘密保持**（範囲、期間、除外事由の妥当性）
- **競業避止・直接取引制限**（期間、範囲の妥当性）
- **契約不適合責任**（通知期間、追完方法）
- **検収・みなし合格条項**（期間、自動合格の条件）
- **支払条件**（期限、遅延損害金）
- **解除事由**（相互性、催告期間）
- **管轄・準拠法**（東京地裁、日本法の確保）
- **違約金・ペナルティ条項**（過度な制裁の有無）

ステップ1の抽出結果は「先方が特に変更・強調している箇所」として補助的に参照。

各指摘には：現行条文 / 想定される法務指摘 / 理想的な改定文 / 参考 を含める。

**指摘選別の基本方針**：
- **高リスク事項**：法的効力・権利関係に直接影響する条項（知財帰属時期、みなし合格等）
- **定番指摘事項**：村越氏から繰り返し指摘される項目（AIの過剰要求、潜脱行為等）
- **許容範囲の変更**：業界慣行内の調整（契約期間、上限設定、保管方法等）は基本的に受入

**リスクレベルと交渉優先度の付与（品質強化ルール）**：

各指摘に、既存の `severity`（必須/推奨/軽微＝交渉優先度、docxの見出し【severity】に自動反映される）に加えて、**「リスク: 高/中/低」を新たに判定**する。

判定基準：
- **リスク高**：損害賠償・違約金の上限/双務性、知的財産権の帰属、契約解除事由など、金銭的損失や事業継続に直接影響する条項
- **リスク中**：検収・みなし合格、支払条件、秘密保持の範囲・期間など、運用負担や解釈の曖昧さにつながる条項
- **リスク低**：条文の表記ゆれ、形式的な文言修正、存続条項の追加漏れなど、法的効力への影響が軽微な事項

交渉優先度（severity：必須/推奨/軽微）は既存基準のまま使う（高リスク事項・定番指摘＝必須、業界慣行内の調整＝推奨、表記・形式＝軽微、が概ね対応）。

**docx構造は変更しない**：`generate_review_docx.py` の列構成・スキーマは変更せず、`expected_comment`（想定される法務指摘）の本文冒頭に **`【リスク：高／交渉優先度：必須】`** の形式でタグを付記する方式で表現する。`severity` フィールド自体は従来どおり設定し、見出し行の【必須/推奨/軽微】表示と重複してよい（リスクと優先度は別軸のため）。

例：
```
"expected_comment": "【リスク：高／交渉優先度：必須】損害賠償が「乙のみ」負う片務構造になっています。対顧客契約では双務化が原則のため、甲乙双方に同等の賠償義務を課す条文に修正してください。"
```

**相手方の反論予測（品質強化ルール）**：

各改定提案（`proposed_text` を提示する指摘）には、`expected_comment` または `reference` の末尾に1行、**「先方が拒否した場合の想定反論」と「受け入れ可能な妥協案（あれば）」**を添える。

例：
```
"reference": "想定反論：先方から「業界標準の書式であり変更不可」と言われる可能性あり／妥協案：上限額を下げず、賠償範囲を「直接損害に限定」する形で折衷可"
```
妥協案が無い（死守すべき／代替が無い）場合は「妥協案：なし（原則どおり必須）」等、無い旨を明記する。

**⚠️ 村越氏定番指摘：必ずチェックする最頻出パターン（patterns-common.md §14）**：
- 損害賠償が「乙のみ」負う片務構造になっていないか → **対顧客契約では双務化が原則**
- 損害賠償上限が甲乙非対称になっていないか
- 解除権・違約金・相殺権など制裁系条項の片務性
これらは先方雛形・ライトアップ雛形問わず、変更の有無にかかわらず確認すること。

**⚠️ 2026-10 方針更新（patterns-common.md §16〜25 が §12〜15 より優先）**：
- 損害賠償の標準形＝双務・直接かつ通常の損害・**逸失利益／機会損失／間接損害／弁護士費用を除外**・上限は過去12か月の対価。**故意・重過失の除外は置かない**（例外あり：§16）
- 欠落チェック：損害賠償／反社（独立した条文）／存続条項（条番号で列挙）／再委託／催告解除と無催告解除の分離
- 「下請法」の表記が残っていたら取適法に置き換える（§20。AIで作った文案で頻出）

**村越氏のスタンスを踏襲**：
- AIを鵜呑みにしない（過剰要求を避ける）
- 交渉余地を残す（対等・双務化）
- 実務合理性を重視（業界慣行・市場水準）
- 潜脱を許さない（運用でカバーする逃げ道は認めない）
- 先方の追加が許容範囲内のものは「許容」と判断（何でもかんでも指摘しない）

### ステップ5. Word赤入れ文書の生成

`scripts/generate_review_docx.py` を実行。表紙・サマリー表・詳細レビュー・免責を含む。

- 入力 `review_data.json` はスクラッチパッドに置く（中間ファイル）。
- 出力 `output.docx` は成果物なので ユーザーが指定したフォルダ（指定がなければ作業フォルダ）に保存する。

```bash
python scripts/generate_review_docx.py -i <スクラッチパッド>/review_data.json -o <保存先フォルダ>/output.docx
```

### ステップ6. 法務依頼メール（下書き）の生成

`scripts/generate_request_email.py` を実行。件名・4見出し（目的/見解/確認者/本人確認欄）を固定フォーマットで出力。出力 `email.md` も成果物なので docx と同じフォルダに保存する。

```bash
python scripts/generate_request_email.py -i <スクラッチパッド>/review_data.json -o <保存先フォルダ>/email.md
```

**件名フォーマット（正式テンプレ準拠）**：`文章名　先方正式会社名`（【リーガルチェック依頼】等の接頭辞は付けない・全角スペース区切り）。本人確認欄の3項目は一字一句変えない。

**氏名は ◯◯◯ プレースホルダで出力**：`email_meta.sender_name`（冒頭の送信者氏名）と `reviewer_name`（規約確認者氏名）は、アカウント情報等から自動で氏名を埋めず、必ず `◯◯◯` のプレースホルダで出力する。本人確認欄が「確認のうえ送付しました」である以上、送信者本人が最後に手で氏名を記入することを徹底するため。部署名は `◯◯`。

**メール作成方針**：
- **先方への配慮重視**：「基本的には先方提案を尊重する方向」であることを明記
- **論点の絞り込み**：高リスク事項・定番指摘事項のみに限定（2〜3点程度）
- **優先度ラベル不要**：（必須）（推奨）等のラベルは記載しない。法務が判断
- **推奨レベル除外**：軽微な修正提案（存続条項追加、法令名修正等）は記載しない
- **落としどころ志向**：「〜すべき」「死守」ではなく、「〜はいかがでしょうか」の相談口調
- **条項列挙は不要**：箇条書きでの論点羅列はせず、重要論点のみ説明
- **並び順は交渉優先度の高い順**：`review_data.json` の `findings` 配列は、法務メールに渡す前に「リスク高×必須」→「リスク中×推奨」→「リスク低×軽微」の順に並べ替えてから `generate_request_email.py` に渡す（`generate_request_email.py` はコード変更せず、必須→推奨の順で拾う既存ロジックのため、配列側の並び順とseverityの精度が結果に直結する）

**メール文例（見解部分）**：
```
先方からの修正提案について、基本的には受け入れる方向で考えております。
以下の点のみ、過去の法務指摘パターンを踏まえ確認をお願いできますでしょうか。

【確認いただきたい論点】
  1. 第○条（△△）：〜に懸念がありますが、何らかの〜があれば問題ないでしょうか。
  2. 第○条（△△）：〜について、〜でよろしいでしょうか。

その他の点については、先方提案を基本的に受け入れる予定です。
```

MGR以上の事前確認が必要な条件（該当時は注意書き表示）：
- 先方から規約の追記・変更依頼がある
- 先方ひな型を使用している
- 重要条項（違約金・競業避止・損害賠償上限等）の変更がある
- 確認権限保有者：杉山／江戸／田原／川上／塩崎

**⚠️ 重要：MGR事前確認の注記はメール本文に入れない**
「※本件は…MGR以上の役職者による事前確認が必要です／確認権限保有者：杉山／江戸／田原／川上／塩崎」という注記は、**法務（村越氏）へ送るメール本文（`■規約確認者`欄）には絶対に含めない**。これは内部統制のための事前確認であり、社外（法務宛て本文）に書く性質のものではないため。MGR事前確認のリマインドは、メール本文の**外側**（申請者向けの⚠️注意書き）にのみ表示する。`■規約確認者`欄には確認者氏名（◯◯◯）のみを記載する。

### ステップ7. 結果の提示

ユーザーに以下を簡潔に共有：
1. 判定した雛形種別（ライトアップ雛形 / 先方雛形）
2. 判定した契約書種別
3. 先方変更箇所の件数（赤字/トラックチェンジ挿入/削除/コメント）
4. 確認論点の件数（高リスク・定番指摘事項のみ）
5. Word ファイルの保存先パス（`<保存先フォルダ>/output.docx`）
6. メール下書き(.md)の保存先パス（同フォルダの `email.md`）
7. 主要確認論点（2〜3点程度に絞り込み）
8. メールで手動埋めが必要なプレースホルダ一覧

**提示時の留意点**：
- 雛形種別に応じたチェック範囲（変更箇所のみ / 全文）を明示
- 「先方配慮重視」のスタンスであることを明示
- 許容範囲の変更については「交渉不要」として整理
- 「死守すべき」等の強い表現は避け、「確認が必要」レベルに調整

長文説明は避ける。詳細は各ファイルに委ねる。

## 村越氏の指摘スタイル（口調参考）

- 「不当に不利益な内容はしっかり交渉をお願いします」
- 「私的制裁を科される謂れはないということです」
- 「変更履歴を確認してください」
- 「AIを鵜呑みにしないようにしてください」
- 「基本的に潜脱行為は認めません」

過剰に丁寧すぎず、実務的・論理的な語り口を。

## レビュー後の学習（パターン鮮度維持）

村越氏の実際の回答が得られたら、このスキルの想定指摘と突合し、(a) 想定が外れた指摘（想定したが村越氏は指摘しなかった／想定と異なる方向で指摘した）と (b) 村越氏が追加した指摘（このスキルが想定していなかった新規指摘）の2点を洗い出す。洗い出した内容は、該当する `references/patterns-{カテゴリ名}.md`（または共通事項なら `patterns-common.md`）に追記する。追記時は必ず「日付」と「パターン概要（指摘内容の要旨・検出ポイント・改定方針）」をセットで記録し、既存パターンの法的内容は上書きせず追記のみとする。

## 免責（Word/メールの両方に必須）

> 本ドキュメントは AI による予備チェック結果です。最終的な契約締結判断は必ず法務担当（legal@writeup.co.jp）の確認を経てください。

## リソース構成

- `references/patterns-*.md` — カテゴリ別パターン集（10ファイル）
- `scripts/extract_review_targets.py` — 赤字・変更履歴・コメント抽出（最重要）
- `scripts/generate_review_docx.py` — Word赤入れ文書生成
- `scripts/generate_request_email.py` — 法務依頼メール生成
- `scripts/sample_review_data.json` — サンプルデータ

## 依存関係

- python-docx: `pip install python-docx`
- Python 標準ライブラリ: zipfile, xml.etree.ElementTree
- `.doc`（旧形式）は自動変換しない。ユーザーに Word で `.docx` 保存し直してもらってから投入する（この環境に libreoffice/soffice は無い）。

## 最終チェック

- 雛形種別（ライトアップ / 先方）の判定を行ったか
- `.doc` 旧形式はユーザーに `.docx` 保存を依頼してから処理したか
- ステップ1で先方変更箇所を抽出したか（ライトアップ雛形の場合）
- 契約書種別を正しく判定したか
- 共通＋種別固有の両パターンを参照したか
- 雛形種別に応じた精査範囲でチェックしたか（変更箇所のみ / 全文）
- 免責が Word/メール両方に記載されているか
- 成果物（output.docx / email.md）を 保存先フォルダに保存したか
- 本人確認欄3項目が一字一句変わっていないか
- 件名が「文章名　先方正式会社名」形式（接頭辞なし）になっているか
- プレースホルダをユーザーに明示したか
- サマリーは簡潔か
- 各指摘に「リスク：高/中/低」「交渉優先度：必須/推奨/軽微」を付与したか（`expected_comment` 冒頭タグ方式、docx構造は無変更）
- 各改定提案に想定反論と妥協案（無ければその旨）を添えたか
- `findings` を交渉優先度の高い順に並べてから email 生成を実行したか
- ユーザーに「レビュー後の学習」ステップ（村越氏の回答との突合・パターン追記）を案内したか
